> 生成时间：2026-11-05。用途：整份贴给外部评审（GPT）看，请它判断「WM 的路走不通在哪、下一步该做什么」。

> 术语：VLA=视觉语言动作模型（我们只微调它的 64 维「动作 token」）；WBC=全身控制器（把 token 变成 29 关节动作）；WM=世界模型（`s' = f(s,a)`）；A'=我们自采的真实转移语料。

## 0. 一句话版本

我们想让机器人（G1 人形，29 DoF）完成 HumanoidArena 的 7 个长程操作任务。做法是：把 VLA 输出的 64 维动作 token 作为「动作」，用一个**冻结的学习型世界模型（WM）**在想象里滚 20 步，用「机器人状态相对理想参考指令流的漂移」当奖励，只反传这个奖励去微调 VLA 的动作头（**完全不做行为克隆**）。

**结果：想象里的漂移稳定下降 30%（松配置）或 2%（紧配置），真机闭环一点没变好。** 松配置下动作还被推偏到 20°/关节。我们查不出是「WM 不准」还是「奖励目标本身错」，也还没做那个能定案的测量。

## 1. 系统与任务

- 机器人：Unitree **G1，29 DoF** + 3 指手（我们把手部 14 维固定用 base 的输出，即 `--hand-from-base`，手不参与微调）。
- 仿真：**Isaac Lab / Isaac Sim**，任务来自 **HumanoidArena**（7 个任务：DoubleDesk、PPBox、OpenDoor、SitSofa、VisionNavi、Boxing 等）。
- 控制频率：**50 Hz**（`CONTROL_DT = 0.02 s`）；VLA 部署节奏 **2.5 Hz / 每 20 步重规划**（`HA_VLA_EXEC_STEPS=20`）。
- 单次闭环评测：**1000 步（≈20 s）**，任务 = **DoubleDesk**，成功判定用官方 success。**注意：DoubleDesk 示范中位数 939 帧、`success` 在 20 s 内几乎不可能达到**，所以 success 全部为 False（base 也是），只能用「净位移 / 沿示范路径进度 / 漂移」这些代理指标。

`provenance`: `configs/ha_closedloop_pin.json`、`docs/HA_CLOSEDLOOP_PIN.md`

## 2. 三个模型分别是什么

### 2.1 VLA（被微调的那个）

- 底座：**GR00T / Cosmos-Reason2-2B**（VLM 主干 2B 参数，冻结）。
- 动作头：**流匹配（flow matching）动作头**，`action_dim=78`（29 本体 + 3 指手 ×2 + …）、动作视界 40 帧、**推理 `num_inference_timesteps = 4`**。
- 我们微调的部分：动作头 + LoRA（`trainable=33,554,432`，占全模型 2.03%）。主干冻结。
- checkpoint：`runs/groot_sonic_vla_ha_b64_lr1e-5/checkpoint-8000`。
- **流匹配的监督信号是什么（重要，用户特意问）**：原始训练是对**速度场**回归——
  `x_t = (1-t)·x0 + t·x1`，网络输出 `v̂(x_t, t, cond)`，目标 `v = x1 − x0`（`x1` = 标签动作块，`x0` = 噪声），损失 `‖v̂ − (x1−x0)‖²`。**所以原始监督信号就是动作 `a`**（以速度场形式表达）。
- 联合微调时我们把这份监督**关掉**：`lambda_bc = 0`、`token_bc_weight = 0`。真正驱动动作头的只有第 5 节那个「想象漂移奖励」，梯度通过采样路径反传（`--fm-grad-backend pathwise`，4 步采样全程可微）。

`provenance`: `scripts/train_joint_v2.py`、`diff_vla_wbc/fm_bc.py`、`diff_vla_wbc/gr00t_fm.py`、`runs/joint_v8/args.json`

### 2.2 执行器（部署时把 token 变成关节动作）

- **SONIC release decoder（ONNX，冻结，可微）**，部署与训练共用一个执行器（这点我们专门修过：早期训练用 SuperMimic 策略、部署用 SONIC，等于「训 A 部 B」）。
- decoder 观测 994 维（token 64 + 本体感觉（q−default、qd、上一动作）+ 角速度 + 重力，多帧历史堆叠）。
- 关节序有两个：`SONIC_ISAACLAB_JOINT_ORDER`（decoder 侧）与 standard 序（训练侧），我们做了 `A∘B == I` 的硬对拍。

`provenance`: `diff_vla_wbc/sonic_isaac.py`、`diff_vla_wbc/sonic_decoder.py`、`scripts/check_all_contracts.sh`

### 2.3 WBC（生成 A' 语料的策略，也是奖励里 FK/漂移的参考执行策略）

- 训练侧用：**`runs/S1_handover/WBC_A24000_wmvel_cmd.pt`**（SuperMimic 风格策略，MLP `(2048,1024,512,256)`，`obs_mode=paper_obs93`，输入含 64 维 token）。
- 动作约定：`q_target = default_q + a × action_scale`，`action_scale` 由机器人决定（中位 **0.439**，手部 0.075）。后文所有「动作漂移」都用这个尺度换算成角度。
- **注意一个不一致**：两份 A' 语料的 meta 里写的采集策略是 **`runs/S1_handover/exp_WBC_exec_haonly_best.pt`**，不是 `WBC_A24000_wmvel_cmd.pt`。两者动作约定相同（scale/default 来自机器人），但**动作分布不同**。这一点我们还没量化影响。

`provenance`: `runs/a_prime_sonic_exc/*.pt` 的 `meta.wbc_ckpt`、`runs/a_prime_sonic_leash/filtered_std.pt` 的 `meta.wbc_ckpt`

## 4. WM 是怎么训的

**结构**：MLP，输入 **133 维** = `状态 71 + 动作 29 + xi 33`（`xi` 是风格/噪声向量，默认 0）；三层 `2048`；输出 70 维后由 `wm.step()` 组装成下一状态 71 维（旋转分量单独处理）。**确定性、单步映射**（另有 GRU 版实现，但当前产品用的是 MLP）。时间积分 `explicit_dt0.02`。

**训练数据与目标（两阶段）**

| 阶段 | 数据 | 目标 | 步数 |
|---|---|---|---|
| 从零（`wm_scratch_ddp.pt`） | A' windows：**12,000 单步 + 4,000 多步** | 单步 MSE + 多步（20 步自回归回放） | — |
| 增益修复（`wm_gain2.pt`，**当前产品**） | A' 窗口 **80%** + 配对探针窗口 **20%**，stage1 + stage2 | 单步 MSE + 多步 + **`increment_loss`（×2）+ `L_gain`（gain_weight 2.0）** | **800 + 800** |

「配对探针」= 专门为「同一状态、不同动作」采的数据：**7,456 组**，每组同一真实状态 `s` + 4 串真实执行过的动作 + 4 个真实 `s'`（`runs/paired_probe2/gain_pairs.pt`）。

**WM 的验收数（全部实测）**

| 指标 | 数值 | 说明 |
|---|---|---|
| 20 步端点保真 | **0.89 cm** | 喂录制动作，预测 vs 真实 |
| 多步 ratio / corr | **0.98 / 0.99**、corr **0.995** | 预测误差 / 数据自身波动 |
| 单步「动作差分」增益比 | **0.90–1.00**（六通道） | `|Δ_WM| / |Δ_real|` |
| 单步差分方向余弦 | **0.97–0.98**，同号率 98–99% | |
| 单步差分 SNR | pos **3.15**、q **5.02**、linvel **4.56**、angvel **6.50**、qd **3.99** | 信号 ÷ 同状态预测误差 |
| 留出任务（B 半，训练没见过） | pos SNR **3.07**、增益比 **0.98** | 说明增益可泛化 |
| 留出「增益泛化比」 | **1.72**（pos 1.24、quat 4.07、q 1.18、linvel 1.35、angvel 1.28、qd 1.20） | 留出误差 / 训练误差 |
| 三个 WM 单步 SNR 对拍 | `wm_ssm_s0_gain` **0.88** → `wm_scratch_ddp` **2.66** → **`wm_gain2` 3.15** | 同一批真实配对数据、同代码 |

**⚠ 关键缺口**：以上全是**单步**的差分质量。**「同一状态、两串动作、各滚 20 步」的差分质量从来没测过**（也没有这种数据）。20 步的**保真**很好（0.89 cm），但 20 步的**差分**未知。

`provenance`: `probe_wm_multistep.py` 输出、`/tmp/snr_now.py` 与 `/tmp/snr_cmp.py` 实测、`probe_wm_gain_heldout.py`

## 5. 联合微调（我们到底在优化什么）

**损失（`v3` 分支，round-5/6/7/8 用的都是它）**

```
loss = λ_r · ( −return )                       # 主项：想象漂移奖励，λ_r = 5.0
     + act_weight · act_penalty(act_rms / act_eps)   # 动作空间刹车
     + trust_weight · relu(‖Δtoken‖/trust_eps − 1)   # token 空间锚（中心 = base 输出）
     + λ_hand · hand_fm                              # 手部流匹配（手不参与，仅正则）
     + 0                                             # λ_bc = 0、token_bc = 0：完全不做行为克隆
```

- `return` = 在想象轨迹上对**每步奖励**做 γ=0.95 折扣求和（`REWARD_HORIZON` 可只取前 k 步，默认 0=满 H）。
- **每步奖励**（`reward_mode=huber_err`）= 对**误差距离** `√e` 做 Huber（远端线性）：根位置、根朝向（拆 tilt/yaw/yaw_huber）、body 位置/朝向、body 线/角速度、关节 q/qd，权重与 δ 如下：`huber_delta 0.02`、`huber_cap 0.15`、`d_pos 0.05`、`d_ori 0.05`、`d_vel 0.05`、`reward_d_max 0.30`、`root_ori_mode=split_huber`、`tail_weight 2.0`、`yaw_hinge_lambda 0.3`、`reward_vel_scale 1.0`。
- **想象怎么滚**：`imagine_with_tokens` 里，第 t 步用 `tokens[:, min(t, T−1)]` 作为条件，调 WBC（**冻结**）得到动作，再调 **WM（冻结）** 得到下一状态，再算奖励。**H = 20 步**（与部署的 20 步重规划一致）。
- **起点**：`--start-source recorded`，从 `a_prime_sonic_leash` 的真实转移里挑一行作起点，**`--start-max-drift 0.05` 只保留漂移 ≤5 cm 的行（实测保留 61.9%，被选起点漂移 p50 = 2.38 cm）**；然后用当前策略做 **10 步 burn-in**（无梯度）进入策略自己的状态分布。
- **动作空间刹车（这轮重点）**：`act_rms` = 当前策略动作 vs **base**（关掉 LoRA/增量、同一噪声）在每个关节上的 RMS；`ACT_PENALTY=l2` 时 `penalty = (act_rms/act_eps)²`，`act_eps=0.30`、`act_weight=0.8`。**历史版本用的是 hinge（`relu(r/eps−1)²`），eps 以内梯度恒为 0 —— 这是动作被推偏 20° 的直接原因。**

**训练规模**：500 次优化器更新（`batch=8`/卡 × 3 卡 × `accum=1` = 24 个窗口/更新）。3 卡 DDP，约 **4.5 s/更新 ⇒ 37 分钟**。

`provenance`: `runs/joint_v8/args.json`、`runs/joint_v8/v3_config.json`、`diff_vla_wbc/v3_step.py`、`diff_vla_wbc/reward_cfg.py`、`scripts/run_joint_ft_round5.sh`

## 6. 部署与闭环评测

- 服务端：`scripts/ha_vla_latent64_server.py`，`--fm-steps 4`（官方 `num_inference_timesteps`）、`--hand-from-base`、`--state-layout legacy`（与服务端拼出的 46 维状态逐位对拍过）。
- 执行器：`HA_ALLOW_SONIC=1`，SONIC release decoder，`HA_VLA_EXEC_STEPS=20`。
- 每次跑 1000 步、一个 seed、任务 DoubleDesk；dump 每步的 `frame / q / qd / root_pos / root_quat / root_lin_vel_b / root_ang_vel_b / applied / latent`。
- **三个指标**（脚本 `eval_closedloop_progress.py` 与 `eval_closedloop_drift.py`）：
  1. `net`：1000 步的水平净位移（只用来判「崩没崩 / 原地踏步」）；
  2. `prog_end`：终点沿示范路径的进度（0=起点，1=示范终点）；
  3. **真机漂移**（我们新加的，才是「跟得准不准」）：`‖(p_t − p_0) − (ref_t − ref_0)‖` 的 p50，**减掉起点**所以与世界系/reset 位姿无关；朝向同理（相对旋转角）。

### 7.3b v8 的健康门结论（脚本输出，非人工判断）

```
[ft] joint_v8: steps=500 batch=8 accum=1 ⇒ 更新次数 500、每更新 8 窗/卡
[ft] 动作漂移 act/rmse(近30均) = 0.054   frac_out = 0.02
[ft] token 锚 trust/rmse = 0.0644   survival_min = 1.000   grad_max = 162.33
[ft] 想象回报 -2.809 → -2.784   win 率 0.562 → 0.688
[ft] ⚠ grad 峰值 162.3（round-3 崩时 683；round-4 峰值 15）
[ft] ✅ 在可信域内（act/rmse 0.054 ≤ 0.50）：这一型与 round-4 同构，闭环大概率不劣于 base
```

**关键对照**：v8 的 `act/rmse = 0.054` **≈ round-4 的 0.055** —— 而 round-4 是唯一「闭环 ≈ base」的一轮（1.014 ± 0.260 m）。所以 v8 的**预期就是「不比 base 差，但也不明显更好」**；要证实/推翻，只能靠配对闭环。

## 10. 目前仍**无法区分**的三个原因

1. **WM 的「横向（动作方向）」响应在 20 步上不准。** 单步准（0.98/0.97），但复合 20 步后未知；20 步保真 0.89 cm 只保证「沿录制车道」准。
2. **真机对这套动作的响应饱和了。** WM 说「往这推还会更好」，执行器实际推不动那么多（接触/摩擦/限位）。
3. **奖励的目标本身错。** `ret_gt = −2.853`（标签 token）比 base 的 −2.809 更差 ⇒ WM 的「好」与「跟紧参考」不一致；优化器追的是一个和任务目标不完全一致的东西。

**唯一能区分 1 与 2/3 的测量**（尚未做）：在真物理里，**同一状态、两串只差一点的动作、各滚 20 步**，比较「WM 预测的状态差」和「真机的状态差」。给出 20 步差分的 SNR 与符号正确率。成本 ≈ 20–40 分钟（Isaac 有 64 并行环境，2,520 步即可）。

## 12. 2026-11-05 晚：三个「真物理」实验定案（谁错了）

### 12.1 修掉的两个口径 bug

1. **WM 动作序**：`SonicExecutor.act` 返回 STANDARD 序，而 WM 训练数据是 **SONIC/HA 序**（实测 `mean|Δ|=0.000000`）。
   之前 FT 直接把 STANDARD 序喂给 WM ⇒ 动作输入整体置换（置换幅度 1.41，动作量级 0.945）。
   后果量化：同一批动作滚 20 步，**奖励从 +0.0173 变 −0.0584（−438%，翻符号）**、末步漂移误差 +11.1%。
   修复：`SonicIsaacBundle.step` 里换回 SONIC 序；等价性 `max|Δ| = 0.000e+00`。
2. **奖励动作单位**：MDP 的 `(a−a_prev)*action_scale` 用的是 HA 口径，而动作是 SONIC 单位。
   换算 `a_ha = a_sonic*SONIC_SCALE/HA_SCALE` 后与录制 q_target 的真实弧度差 **max|Δ|=2.4e-7**（不换算误差 131%）。
   影响面：`joint_limit` **不吃动作**（用状态 q），`action_rate` 实测为 0.0 ⇒ 实际零影响，但已修。

### 12.2 三个真物理实验（同 48 个窗口、δ=0.15 SONIC 单位 ≈3.3°/关节、各滚 20 步）

| 方向 | WM 的判断 | 真物理里"+"更好 | 真物理漂移变化 |
|---|---|---|---|
| **∂J_WM/∂a（WM 梯度）** | + | **33/48 = 69%** | **−1.23 cm（变好）** |
| **FT 实际造成的动作位移**（闭环 dump 里 base↔ftv10 的 `applied` 差） | +（ΔJ=+0.029） | **17/48 = 35%** | **−0.11 cm（略变坏）** |
| 参照：WM 自身的 20 步保真误差 | — | — | 0.89 cm |

### 12.3 结论（定案）

* **WM 没训错**：它的 20 步梯度方向在真机上是**有效的**（69% 同号、漂移 −1.23 cm、信号/误差 ≈1.4）。够用但不精确。
* **错在联合微调的"方向落实"**：FT 用 0.17 的动作位移（≈4.3°/关节）在真机上反而把漂移抬了 **+4.5 cm**（8 对配对，2/8 更好）；而同样量级沿 WM 梯度方向是 **−1.2 cm**。
  ⇒ **FT 最终走的方向，不是动作空间里的上升方向。**
* 扭曲最可能来自 **token → 4 步流匹配采样 → 动作** 这一条链的雅可比（以及长期饱和的 trust 锚、act 刹车的对抗力）。
* 因此：**不需要重新采集，也不需要重训 WM**；要改的是**联合微调的更新方式**。

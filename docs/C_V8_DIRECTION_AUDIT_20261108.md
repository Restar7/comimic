## 1. 为什么要做这个实验

评审（以及我们自己的历史）指出两层断链：

1. **WM 的方向**：已验证有效——48 窗口 **69% 同号、真实漂移 −1.23 cm**；H=20 复测 **98.4% 同号**；
2. **Actor 是否照做**：2026-11-05 对**旧 FT 配方**实测过：WM 方向 33/48=69%，但 **FT 实际造成的动作位移只有 17/48=35%**，
   而且真机漂移几乎没改善（−0.11 cm）。

⇒ C-V8 是否也复现了同样的"方向没落实"？**之前没有任何数据回答这个问题**（24 集闭环没开 dump，
也没有 C 的真实 20 步 rollout）。本实验是它的**离线上游**：
不测"真实物理是否改善"，只测"**token 位移是否指向 WM 认为更好的方向**"。

## 2. 方法（可复现，脚本已落盘）

```
脚本：scripts/probe_c_v8_token_direction.py
产物：runs/three_track_v8/c_tracking_recovery/dir_probe_test_v2/test.json
数据：runs/temporal_ac_bptt_v5/eval_set 的 test split（96 窗口，H=20）
      Windows 里固化了 frames / clip_id / refs_f = frames+1..20（同一条参考的后续 20 帧）
模型：FT8000 + LoRA16（actor_wm0_p2p4/checkpoint_lora_best.pt，it=250）
      + 冻结 WM0（wm_gain2.pt, sha fc5aeb30…）
```

每个窗口：

1. **成对采样**：`tokens_C`（LoRA 开）与 `tokens_base`（`lora_scale=0`，即 pristine），
   **同一个 seed ⇒ 同一个 flow 噪声**（`GradVLASampler.sample_paired`），所以 Δtoken 里没有采样噪声；
2. **求梯度**：把 `tokens_C` 设为叶子，跑 WM 的 20 步想象 rollout 得到 J20，`g = ∂J/∂token`；
3. **指标**：
   * `cos = <Δtoken, g> / (|Δtoken||g|)`；
   * `ΔJ = J(tokens_C) − J(tokens_base)`（真实 WM 差，即报告里的 ΔJ）；
   * `ΔJ_lin = g·Δ`（一阶预测）；
   * `ΔJ_opt = |g||Δ|`（**同幅度、沿梯度**走的一阶上界）。

> 注意：**只有前 20 帧 token 进入 J20**（`imagine_with_tokens` 用 `tokens[:,t], t<20`），
> 所以额外报了"只用前 20 帧"的 cos，作为更严格的口径。

## 3. 结果

### 3.1 主表（96 窗口）

| 指标 | mean | median | 分布 |
|---|---|---|---|
| **cos（全 40×64 = 2560 维）** | **+0.0781** | +0.0831 | p10 −0.0447 / p90 +0.1943；83% >0；**0% >0.5** |
| **cos（只用前 20 帧 = 1280 维）** | **+0.1062** | +0.1150 | 83% >0；**5.2% >0.3**；0% >0.5 |
| 随机基线 | 1/√1280 = **0.0280** | — | 实测 0.106 ≈ **3.8σ** |
| **ΔJ（复算）** | **+0.01640** | +0.01484 | 85% 为正 |
| **ΔJ_lin = g·Δ** | +0.01406 | — | 与 ΔJ **corr = 0.964** |
| **ΔJ_opt = |g||Δ|** | **+0.1906** | — | 是实际 ΔJ 的 **11.6 倍** |

* `|Δtoken| = 2.093`（2560 维范数），`|g| = 0.5048`。
* 逐 batch 的 cos（说明不是某一个 batch 的偶然）：
  `0.091 / 0.061 / 0.079 / 0.110 / 0.054 / 0.073` —— **6 个 batch 全部在 0.05–0.11**。

### 3.2 三个可以直接读出来的结论

1. **ΔJ 复算 = +0.01640，与报告逐位一致** ⇒ 探针的 J 口径与评测完全一致，不是另一个目标函数。
2. **`ΔJ_lin` 与 `ΔJ` 相关 0.964** ⇒ 更新处在**线性区**，所以"cos 低"不能用"非线性/饱和"解释，
   它确实就是**方向问题**。
3. **方向效率 ≈ 1/11.6**：同幅度沿梯度走能拿到一阶上界 +0.1906（当然会饱和，实际拿不满），
   而现在只拿到 +0.0164。

### 3.4 checkpoint 扫描：**cos 全程平**（这条排除了"累积漂移"）【FACT】

脚本 `scripts/probe_c_v8_token_direction_ckpts.py`（一次加载模型，循环 5 个 checkpoint；
pristine token 只算一次并缓存，保证每个 checkpoint 的 Δ 都用同一份基线）。
产物：`runs/three_track_v8/c_tracking_recovery/dir_probe_ckpts/curve.json`

| it | cos(all) | **cos(前 20 帧)** | 中位 | **ΔJ（test）** | ΔJ_lin | ΔJ_opt | 效率比 |
|---|---|---|---|---|---|---|---|
| 50 | +0.087 | **+0.119** | +0.131 | +0.01200 | +0.01111 | 0.1319 | 11.0× |
| 100 | +0.074 | +0.101 | +0.099 | +0.01464 | +0.01281 | 0.1730 | 11.8× |
| 150 | +0.070 | +0.096 | +0.096 | +0.01335 | +0.01218 | 0.1831 | 13.7× |
| 200 | +0.075 | +0.103 | +0.110 | +0.01542 | +0.01333 | 0.1943 | 12.6× |
| 250 | +0.078 | +0.106 | +0.115 | **+0.01640** | +0.01406 | 0.1906 | 11.6× |

**三条读法**：

1. **cos 是平的**（0.096–0.119，波动 ±0.01 ≈ 噪声），**不是"先高后低"**
   ⇒ 如果低 cos 只是"280 步 SGD 累积漂移"，it=50 时应该明显更高。**没有。**
2. **收益靠"把位移做大"，不是"把方向修正"**：
   ΔJ +37%（0.0120→0.0164），ΔJ_opt +45%（0.132→0.191），**cos 不变**
   ⇒ 训练只是在**同一条偏了约 84° 的方向上越走越远**；
   这也解释了为什么 it=100 之后会平台化（位移继续变大，但线性收益饱和 + 物理代价上升）。
3. **效率比全程 11–14×**，没有任何改善。

⇒ **问题在结构层，不在训练动力学。**

## 4. 这说明了什么：**Situation C**

评审给的三种情形：

* **A**：WM 说改善 + Isaac 真实 20 步也改善 + 完整任务没改善 ⇒ 局部信号可落地，问题在长程；
* **B**：WM 说改善 + Isaac 真实 20 步变差 ⇒ WM 在 Actor 动作分布上预测/优化有偏；
* **C**：小幅人工扰动有效，但训练后的 Actor 动作无效 ⇒ 问题在 LoRA/参数更新/FM/SONIC 的雅可比。

**本实验落在 C 的上游**：
* WM 方向有效（69%/98.4%，两次真物理）；
* **但 Actor 的 token 位移只有 ~10% 沿这个方向**；
* 且那 10% 的投影**恰好**解释了全部 +1.04%（相关 0.96）。

⇒ **不能再用"C 的离线收益小"来怀疑 WM；也不能指望刷新 WM 能解决问题**——
即使 WM 100% 准，Actor 只执行 10% 的方向，收益也只会是现在的量级。

> 注：这不等于"C 什么都没学到"。它确实学到了**一点点**正确方向（83% 的窗口投影为正，
> 合计 +0.0164，CI 不含 0）。问题是**方向效率太低**。

## 5. 顺带发现：val 与 test 的 reward 口径不一致【FACT】

`scripts/eval_c_v8c_test.py` 调用的是 `d03.load_env(device)`，**没有传 `bptt_args`**，
而 `load_env` 里是：

```python
bargs = json.loads(Path(bptt_args).read_text()) if bptt_args else {}   # ← 空字典
apply_reward_cfg(bundle, bargs)                                       # ← 全部走默认值
```

于是：

| 项 | 训练 val（train.log 打印） | 独立 test（报告的 +0.01640） |
|---|---|---|
| reward `term_off` | **1**（survival ≡ 1） | **0**（soft termination 生效） |
| `d_max` | **0.3** | **0** |
| 其余（mode/vel_scale/huber/tail/yaw） | 相同 | 相同 |

⇒ **val 与 test 不是完全同一口径**（数值上接近：val best +0.01748 vs test +0.01640）。
修法：`eval_c_v8c_test.py` 显式传 `--bptt-args runs/bptt1/args.json`。
本探针与 test 用的是同一套（默认）口径，所以 §3 的 ΔJ 能和报告对上。

## 10. 限制与边界（评审请重点看）

1. **cos 是"相对最终点局部梯度"的**，不是"训练全程是否跟随"；它衡量的是"最终位移是否指向
   当前 WM 认为更好的方向"，而不是训练动力学。
2. **ΔJ_opt = 11.6× 是一阶上界**，沿梯度走那么远必然饱和（J 上限 1.821），真实可达远小于 0.19；
   但它足以证明**方向差距**是真实的。
3. **只用了 test 96 窗口**、单个 adapter、单 seed；没有跨 seed 的方差估计。
4. **没有测真实物理**（Isaac）；"WM 认为更好"≠"物理更好"。这是 §8 里 P2 要补的。
5. 探针用的是 `load_env` 的**默认 reward 口径**（与 test 一致，与训练 val 不同，见 §5）。

## 11. 给评审的 5 个问题

1. **cos ≈ 0.10 的解读**：你会把它读成"LoRA 只学到 10% 的方向"，
   还是"280 步 SGD 的累计位移本来就不该和最终梯度对齐"？判别方法是什么？
2. **物理项折中**：物理项有效梯度是 J 的 1.12×（`L_added` 与 J 的 cos=−0.371）。
   你会先关掉物理项做对照，还是先做梯度手术（PCGrad 之类）？
3. **低秩约束**：rank16 × 218 层的 LoRA，其可达 token 子空间有多少维？
   有没有便宜的办法估计"g 落在 LoRA 可达子空间内"的比例？
4. **真实 20 步 ΔJ**：如果只能做 24 个窗口，你会怎么选窗口
   （按任务/按困难阶段/按 cos 高低分层）才能最大化信息量？
5. **优先级**：在"提高方向效率"与"换任务级目标"之间，你会先做哪个？为什么？

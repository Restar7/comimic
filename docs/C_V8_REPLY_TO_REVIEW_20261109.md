## 1. 你的第 1 条：我们查出一个**真 bug**（不是 History，是动作序）

### 1.1 我们查了什么

你说"WM 用想象状态滚动更新 History 解码动作，Isaac 用固定 History 提前解码 20 个动作，
所以 `a_t^WM ≠ a_t^Isaac`"。

查代码后发现：**这一层其实是对的** —— 我们的评分函数是把 **Isaac 实际执行的那 20 个动作**
（`job["acts_plus"]` / `job["acts_minus"]`）**原样**喂给 WM 做 20 步 rollout，不是重新解码。

**但同一段代码里有一个更致命的错**：我们用的是**裸 bundle**（`load_isaac_bundle`），
**绕过了 `SonicIsaacBundle.step` 里唯一那处换序**：

```python
# diff_vla_wbc/sonic_isaac.py  SonicIsaacBundle.step()
act_wm = action.index_select(-1, self.executor._std_to_ha)   # STANDARD → SONIC/HA 序
self.base.step(state, act_wm, xi, step_idx)
```

* WM 是用 **A′ 语料的动作（SONIC/HA 序）** 训的；
* 策略 `/ SONIC decoder` 输出的是 **STANDARD 序**；
* 直接调 `load_isaac_bundle(...).step` ⇒ WM 收到**被置换过**的动作
  （代码注释里写得很清楚：置换幅度 ≈1.24，而动作量级只有 0.945）。

⇒ **v1 报告里的 ΔJ_WM = +0.00680 是错的。**

### 1.2 修复后（v2）

| | ΔJ_WM | ΔJ_Isaac | 符号一致 | A/A ΔJ_Isaac |
|---|---|---|---|---|
| **v1（错）** | +0.00680 | −0.00532 | 54% | mean +0.00022 / std 0.00227 |
| **v2（对）** | **+0.00950**（71% 正） | **−0.00733**（**25% 正**） | **46%** | mean **+0.00067** / std 0.00387 |

* 18/24 窗口真物理变差，符号检验 **p = 0.0227**；
* 主效应 −0.00733 = A/A 均值噪声的 **11 倍**；
* 分任务：OpenDoor −0.00123（≈持平）、SitSofa **−0.00726**、VisionNavi **−0.01350**；
* `corr(ΔJ_WM, ΔJ_Isaac) = +0.267`，`corr(cos, ΔJ_Isaac) = +0.342`。

**结论方向不变、幅度更大。**

**动作序的直接验证（补做）**：用同一批动作按两种口径滚 WM，与真实 Isaac 每步状态比 RMSE ——
不换序 **1.864** vs 换序 **1.790**（−4%）。⇒ v2 的口径更符合训练；但"状态 RMSE 只差 4%，
ΔJ_WM 却差 40%"，说明**收益量对动作序远比状态预测敏感**。A′ 单步重放也给出同样结论
（原序 2.592 vs 置换 3.395/2.837）。

### 1.3 你说的另一半仍然成立（我们完全承认）

**这 20 个动作本身是开环解码的**（固定初始 10 帧 obs 历史）。
真实闭环里 SONIC 每个 tick 都会从真实状态重算 obs 历史 ⇒ **动作序列会不同**。

所以现在的位置是：

| 层面 | 状态 |
|---|---|
| Isaac 执行的动作 vs WM 收到的动作 | ✅ **同一批数组、且关节序已正确**（v2） |
| 这批动作是否 = 闭环部署会产生的动作 | ❌ **否**（开环）⇒ **最大软点，需要闭环 H20** |

## 2. 你的"最小修复"（固定动作重放）——已经做了

你建议：*"取已经提交给 Isaac 的 C 和 Base 各 20 个真实命令动作，让 WM0 从同一 71 维起点、
严格使用这 20 个固定动作预测，期间不重新调用 SONIC；用完全一致的参考和 Reward 计算 WM 与 Isaac 的 ΔJ。"*

**这正是 v2 做的事**（也是 v1 想做但做错的地方）：

```
job["acts_plus"]  (C)   → WM 20 步 rollout（SonicIsaacBundle.step）  → ΔJ_WM(+)
job["acts_minus"] (Base)→ 同上                                        → ΔJ_WM(−)
roll["states_plus/minus"] (真 Isaac 每步后状态) → 同一 reward         → ΔJ_Isaac
reward 配置统一到训练口径（term_off=1, d_max=0.3）
```

**判读（按你的标准）**：

> "若固定动作重放后，WM 也预测 C 更差 ⇒ 先前正负矛盾可能混入执行协议不一致。"

我们得到的是**反过来的情况**：WM **仍预测 C 更好**（+0.0095），而 Isaac 更差（−0.0073）。
⇒ **按你的判据，这属于"更直接的 WM 模型偏差证据"**，而不是执行协议不一致。

**但仍有一个例外条款**：这些动作是开环解码的，**不在 WM 训练时的闭环动作分布上**。
所以严格说，它证明的是"**WM 在这批开环动作上的收益判断是反的**"，
还不能直接说"WM 对部署分布也错"。

## 3. 你要求的闭环 H20：同意，且已经列出工程口径

参数（与部署一致，不另设计控制链）：

| 项 | 口径 |
|---|---|
| 起点 | 同一窗口的完整物理起点（**需要完整快照**，不只是根+关节——见 §5 局限） |
| Token | 同一 flow 噪声下 Base / C 各一份 40×64 chunk |
| 逐 tick | SONIC 读**当前真实 obs 历史** + `token[t]` → 动作 → PD → Isaac → 新状态 → 更新历史/prev_action |
| 评分 | 训练口径（term_off=1, d_max=0.3）+ 另报"不含终止项"的 tracking 分 |
| 规模 | 24 窗口（不扩大） |
| 实现路径 | 首选 `SM_TOKEN_SOURCE=npy` 回放（token 流喂给 SONIC provider）；备选在线 server |

**注意**：`SM_TOKEN_NPY` 回放是"逐 tick 由 provider 自己算 obs 历史"，正是我们要的。
但它默认从 env reset 状态开始，**必须确认能注入我们的起点状态**——这点我还没验证。

## 4. 你说我们"把负收益归因于 92% 非梯度分量"——这个归因已撤下

你的原话：*"梯度投影比例不能直接分解真实物理回报损失；要验证这个解释，必须做受控动作干预。"*

**同意，已从 v2 的结论里删掉这个因果说法**，改成待做实验：

```
Δtoken = α·ĝ + Δ⊥        （ĝ = ∂J/∂token 方向，Δ⊥ 正交分量）

各 24 窗口 → 看真实 J 的分解
```

这才是"分量归因"的正确做法。成本约半天。
